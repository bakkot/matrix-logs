<Lea Verou>

To elaborate, this was most of my feedback (largely thinking out loud):

  • In the spirit of Simple things should be easy, complex things should be possible, it feels wrong to use an array at all times, since sequence units are the more niche use case and shouldn't get in the way of simple use cases. Complexity should be progressively revealed when it becomes relevant. If you don’t need sequence units, nothing in the API should force you to deal with how sequence units are handled.
  • Polymorphism in the input seems fine (per robustness principle: be liberal in what you accept). But I agree polymorphism in the output is a footgun.
  • Thinking: Sequence units always have a simple unit equivalent, right? Another way to handle this might be two properties, where .value would be the equivalent simple value of the first unit.
  • OTOH, if you specify a length in X ft Y in, it seems useful to get the equivalent total ft OR total in. And vice versa. Of course there is convertTo(), but it feels fundamentally distinct from conversions like e.g. feet to meters. Essentially, is it really a different unit, or just a way to ensure precision for a certain format? If the latter, should the API make it that distinct? E.g. it can be stored internally so it can be used for precision reasons when relevant.
  • If we go with multiple properties, would it be more useful to have e.g. .feet and .inches instead of .value? What would value be if singular, feet or inches? But if it's named properties, you have a different object shape for different units, which is not exactly exotic but still kind of not ideal. Though there is precedent.

Anyhow, just some unstructured thoughts, I'm much more convinced that .value always being an array is not the right solution, than what the right solution is.
